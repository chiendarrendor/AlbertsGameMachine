Part of [[project-overview]]. Covers the contents of each game's `<Game>Server.xml` file (see [[games-overview]] for the per-game directory layout; e.g. `OutpostServer.xml`). This is the concrete XML realization of [[game-spec-language]]'s FSM concept, compiled to C++ by the Perl compiler (see [[component-perl-compiler]] once written) and executed against [[component-game-dlls]]'s `<Game>State`.

**Top-level contents of `<Game>Server.xml`:**
1. A list of allowable FSM states (the turn/phase/step values from [[game-spec-language]]). **Two states are implicit and never appear in this declared list:** `InitialState` and `TerminalState` are automatically added by the state-engine machinery generated during DLL compilation (not authored per-game). `InitialState` is where the `StateWalker` object points immediately on instantiation of a new gameplay (i.e. before any Transition has run). Entering `TerminalState` signals the state engine that no further actions will ever occur on that gameplay (game over). A Transition referencing `InitialState`/`TerminalState` as `from`/`to` without a corresponding `<state>` declaration is correct, not a bug/oversight.
2. Descriptors for all Events the server can send to the client (see [[protocol-terminology]]). **Some Events are implicit, like the implicit states above:** the event compiler (part of the [[component-perl-compiler]] tooling) automatically creates a number of built-in Events not declared in any `<Game>Server.xml`. Most of these are internal core-server-to-core-client plumbing (framework-level, not game-rules-level) and never appear in game code. The one exception game code actually uses is **`RESET`** — usable/sent from game-specific transition bodies despite having no `<event name="RESET">` declaration in the XML.
3. A set of **Transition** objects — each Transition maps 1-to-1 to an Action.

**Transition object fields:**
- **Unique name.**
- **`from` / `to` states** — the edges of the FSM graph. Shorthand `cyclic <state name>` means from == to (very common: an action that doesn't change FSM state, e.g. buying one item during a "buy things" phase loops back to the same "buy things" state so the player can buy again).
- **`allowed` (boolean)** — gates whether the server will accept this Action at all, independent of arguments. Common case: gating by whose turn it is — if it's not your turn, actions are generally not `allowed` regardless of what arguments you'd supply.
- **Action arguments** — the specific parameters an Action of this type needs (e.g. a MOVE transition needs: which piece, destination space), plus verification logic that the supplied arguments describe a legal move from the current game state. This is a distinct concern from `allowed`: `allowed` asks "can you attempt this kind of action right now at all?"; argument verification asks "given that you can attempt it, is this specific attempted move legal?"
- **Body** — only executed if both `allowed` is true AND the arguments verify as legal. Contains the actual code that mutates the `<Game>State` object and emits the resulting Events to the client.

**`auto` transitions:** When a transition has `allowed` set to false, it may instead set a separate boolean `auto`, marking a state transition the game engine takes automatically on the game's behalf, with no direct player Action triggering it. Example: in an "is everyone ready?" state, each player individually takes an "I am ready" Action; once all players have done so, an `auto` transition fires by itself to advance the FSM to "beginning of first turn" — no player explicitly causes that specific transition.

**`refresh` body:** A special designated body (separate from the normal per-transition bodies) whose job is to generate *every* Event needed to fully describe the current game state from scratch. Normal transition bodies only emit Events for whatever that specific transition actually changed (deltas). `refresh` exists because sometimes a full snapshot is needed instead of a delta: when a new observer joins a room, or a player leaves and re-enters, the client has no prior Event history to reconstruct state from, so the server needs to replay the complete current state as Events.

**Known pain point / future rearchitecture (tracked in `TODO.md`, see [[roadmap-todo]]):** Albert considers the current model cumbersome — manually specifying Events for every state change in every transition body, plus manually keeping `refresh` in sync with all of them, is error-prone and duplicative. Candidate redesign (large, likely phased): represent game state as a structured object (JSON floated as a possible format); at the start of each transition body, mark the whole state "clean"; have the state's own mutators automatically mark whatever they touch as "dirty"; then at the end, either (a) send only the dirty parts as Events, (b) send the whole state with dirty parts flagged, or (c) — leaning on modern network/CPU headroom — just resend the entire state every time and make the client GUI stateless rather than delta-driven. This would replace hand-authored Events and hand-maintained `refresh` bodies with something auto-derived from state mutation itself.

**How to apply:** When debugging "why didn't my action do anything" or "why was my action rejected," check in this order: (1) is there a Transition at all mapping to this Action from the current FSM state, (2) does `allowed` evaluate true, (3) do the action arguments verify — only after all three does the body run. When adding a new player-facing action to a game, this is the four-part shape to fill in: from/to (or cyclic), allowed condition, argument verification, and body. When a state change should happen without any player pressing a button, reach for `auto` (with `allowed: false`) rather than trying to fake it as a player Action. Whenever adding new per-transition Events for observable state, double check whether the `refresh` body also needs updating to include that same state, since it's a separately-maintained full snapshot, not auto-derived from the incremental transition bodies.
