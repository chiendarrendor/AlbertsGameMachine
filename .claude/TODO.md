# Game Machine TODO

- [ ] **Add a per-game-instance unique identifier to the FSS envelope, and have the client globally reset the GUI whenever it changes (Albert, 2026-10-21, not started, needs design).** Surfaced while converting `ShipList`/`ShipItem` off the old event model: `ClientManager.HandleGamePacket` only rebuilds the widget tree (`GUIUnit`/`m_game`) when the *game name* changes ("Outpost" → "MerchantOfVenus"), never when it stays the same but the underlying *instance* changes — e.g. a player moving from one room's Outpost game to a different room's Outpost game, or a room's game being reloaded from an unrelated save file. In both cases every widget's accumulated local state (selections, cached snapshots, reset-on-state-change tracking like `StateSensitiveTextBox`'s) silently survives into a game instance it has nothing to do with, and nothing in `GuiPacketParser` (`getGameName`/`getXMLLoc`/`getXMLFile`/`getStateName`/`getStateDesc`/`getBody`) carries any room/instance identity to detect this by. Albert's proposed fix: a unique id generated per game instance (assigned at creation, persisted through save/load so a *reload* of the same instance keeps its id but a *different* save file gets a different one), sent automatically in every FSS's envelope (state/legalActions level, not the per-game `body` — this needs to be generic across every game, not an Outpost-specific field); client-side, whenever two consecutive FSS for the same `gameName` carry different instance ids, throw a global reset through the whole GUI tree before handing the new FSS to it, so no individual widget author ever has to reason about "is this actually the same game as last time" — that question gets answered once, centrally, not reinvented ad hoc in every widget (which is explicitly the thing being avoided: per-widget heuristics like comparing player rosters were considered and rejected as exactly the kind of brain-bending special-casing this should make unnecessary). This also directly closes a real security/correctness gap in load/save: today, loading an unrelated save file into a room swaps out who's "supposed" to be playing with zero signal to anyone already seated there (e.g. a player maliciously or accidentally loading a save from a completely different trio of players). Deliberately scoped down for now to documenting the problem and the intended fix — not implemented. Current widget conversions (`ShipList`, `StateSensitiveTextBox`) are proceeding without any interim per-widget workaround for this, on the basis that the real fix belongs at this layer, not scattered across individual widgets.

Given this system is near end-of-life and MerchantOfVenus's client already went "one giant custom widget per game," Albert's call was not to generalize the fix (e.g. teaching `WindowNode` about `JLayeredPane`) but to repurpose `Players.xml`'s already-existing (commented-out, pre-Phase-3, dead) `PlayerWindow` stub into the sole `<javaclass>` for that window, constructing `ItemStockGrid`/`ShipList`/`TurnOrder`/`PlayerDisplay`/`OptionPanel` directly as plain Java objects in a `JLayeredPane` and fanning out `HandleEvent`/`Refresh`/`Reset` to them by hand. `JLayeredPane` already had a precedent in this codebase (`MerchantOfVenus/client/MerchantOfVenus/PopAndLockPanel.java`).
  - **Sizing the two `JLayeredPane` layers needed a custom `LayoutManager`, not `OverlayLayout` or `GridBagLayout`'s anchor** — both empirically confirmed to stretch/center in ways that don't give "one layer fills, the other sits at its own natural size in a fixed corner" (see `PlayerWindow.LayerLayout`'s own comment for the specifics). Getting the *lower* layer's own internal left-justified stacking right needed a second round: `ShipList`/`TurnOrder`/`PlayerDisplay` all build their real content *lazily* inside their own `HandleEvent` (constructors leave an empty panel), so a one-time `setMaximumSize(getPreferredSize())` snapshot taken right after construction froze them at their near-empty starting size forever; fixed with a `ShrinkWrapPanel` whose `getMaximumSize()` tracks `getPreferredSize()` live, plus an explicit `invalidate()`/`doLayout()` on the lower content after every `HandleEvent` fan-out (confirmed empirically that `BoxLayout` caches child size requirements and doesn't reliably notice a *grandchild's* preferred-size growth from the normal `invalidate()` cascade alone).
  - **One real, previously-latent bug surfaced and fixed along the way, unrelated to the migration itself but found while building `OptionPanel`:** `ActionVarNode.ParseTypedValue` does `Boolean.valueOf(rawValue)` for `paramtype="bool"` vars, which only ever recognizes the literal string `"true"` — the old `OptionRow`/`OptionSelector` convention of reporting `"1"`/`"0"` would have silently always parsed as `false` regardless of the checkbox's real state. `OptionPanel`'s own generators report `String.valueOf(boolean)` instead. (`OptionRow.java`/`OptionSelector.java` themselves were left as-is rather than patched, since they're retired by this migration, not deleted outright.)
  - **A second, independent latent bug found once a real game could finally be played far enough to trigger it:** `GameGui.HandleFullState` dispatched *every* full-state envelope to the whole widget tree unconditionally, including `"sequence"`-type responses (body shape `{sequence,firstIndex,records}`, nothing like a normal game body) — any widget naively querying the body for a normal field (`BidItemWatcher` querying `"supplyShip[]"`) threw `JsonQueryException` the moment a real Spends-sequence fetch happened. Fixed by gating the widget-tree dispatch on `ActionContentType.TRANSITION`; `SequenceManager.update(gpp)` still runs unconditionally since it already discriminates transition vs. sequence internally. This had been latent since the Sequences work landed — it just needed a game to actually reach a real purchase to surface it.
  - **Also removed while here:** the vestigial pre-Phase-3-Applet-era `JFrame` (`ClientApplication.java`, title literally `"Test"`) wrapping an otherwise-unused `ClientPanel` — it turned out to be the *only* window in the whole app with real `EXIT_ON_CLOSE` behavior (`TabbedWindow`/every `WindowNode` frame are deliberately `DO_NOTHING_ON_CLOSE` with no listener of their own), so that responsibility moved onto `TabbedWindow` itself via an explicit `WindowListener` in `ClientManager`'s constructor (`dispose()` then `System.exit(0)`) before the wrapper was deleted.
