The real "invention" here is the FSM-and-game-state-manipulation model (see [[game-spec-language]]), not the XML syntax it's currently expressed in — so XML isn't load-bearing to the concept. See [[component-perl-compiler]] and [[game-server-xml]] for what this would replace. **Reframed 2026-09-27 (Albert), tentatively "Phase 4" of the same overall redesign, deliberately not started or blocking Phase 1B:** `transitioncompiler` wasn't, even at the time, the best solution to the problem — the "game rules language" was never really the XML syntax at all, but a **Pattern** (Gang-of-Four sense): an FSM whose transitions are concrete subclasses of abstract per-transition superclasses, driven by a generic walker/dispatcher. That pattern is what's actually load-bearing, not the compile step that currently produces it. Two candidate ways to realize the pattern directly, without a code generator: (1) C++ template metaprogramming, expressing transitions as concrete subclasses instantiated over template parameters instead of Perl-emitted `.cpp`; (2) implement the same pattern directly in another language (Python is the specific candidate, tying back to Phase 1's own original motivation — Albert chose process decoupling specifically so games could eventually be written in something other than C++) using ABCs for the abstract transition/state superclasses and runtime introspection in place of a compile-time code generator.
